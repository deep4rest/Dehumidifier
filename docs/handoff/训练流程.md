# 单 KAN 训练流程与数据契约

本文依据当前 `training/single_kan/`、`training/src/kan_model.py` 和 `simulation/dual_rotor_sim/scalers.py` 的实现整理，供另一台电脑的 Agent 接手。入口、权限与目录规则以根目录 `AGENTS.md`、`README.md` 为准；气路、流量参考基准、联立求解及压力边界见[系统拓扑与物理契约](系统拓扑与物理契约.md)。历史 `archive/` 训练器、候选模型、路由表和设计记录不能替代当前入口。

本次 GitHub 移交仅包含代码、配置和说明。两份原始 XLS、模型权重、scaler、checkpoint、训练/仿真记录及 ONNX/DLL 成品均需留在本地或带外移交；clone 仓库不会自动获得训练数据和可用模型。用户上传源码的授权不包含执行全量训练，接手 Agent 必须取得明确全量训练授权后才使用 `--confirm-full`。

## 1. 另一台电脑的最短接手顺序

建议使用 Linux 或 Windows WSL，从仓库根目录操作。虚拟环境不复制到新电脑，使用本机 Python 重新创建：

```bash
git status --short
python3 -m venv .venv
.venv/bin/python -m pip install --upgrade pip
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m pip install -e simulation/
.venv/bin/python -m training.single_kan.train --help
```

依赖文件使用最低版本范围，没有锁定全部依赖版本；另机得到的 PyTorch、NumPy、scikit-learn 版本可能不同。需要严格数值复现时，应同时带外保存原环境版本、Python 版本、CPU/GPU 与 CUDA 信息，再复查差异；固定 seed 不保证跨设备逐位一致。`.venv/` 是训练和仿真共用环境。

纯源码 clone 后可以直接运行默认回归。测试以 `requires_data` 标记依赖带外权威 XLS 的用例，以 `requires_models` 标记依赖外部历史模型/配置的用例；相应文件缺失时默认 skip，其他代码回归继续运行：

```bash
.venv/bin/python -m pytest -q
```

也可以先只检查使用合成数组的训练契约和训练器回归：

```bash
.venv/bin/python -m pytest -q \
  training/single_kan/tests/test_data_contract.py \
  training/single_kan/tests/test_model_trainer.py \
  training/single_kan/tests/test_review_regressions.py
```

skip 只表示外部资料缺失，不表示对应数据集成或模型回归通过。需要严格检查外部资料和相关用例时执行：

```bash
REQUIRE_EXTERNAL_FIXTURES=1 .venv/bin/python -m pytest -q -m 'requires_data or requires_models'
```

严格模式下缺少所需文件会失败；`requires_models` 包括历史对照模型/快照，单纯训练生成当前两个单 KAN 包并不能补齐全部历史模型资料。执行这组严格测试前应查看用例所需路径并带外恢复对应资料，不能把历史模型拿来替代当前仿真模型。没有历史资料时，应如实报告相应验证未完成。

按下一节恢复并核验权威 XLS 后，再执行完整回归与有界 smoke：

```bash
.venv/bin/python -m pytest -q
.venv/bin/python -m training.single_kan.train \
  --profile all --smoke-test --max-steps 4 \
  --validation-interval-steps 2 --checkpoint-interval-steps 2 --no-progress
```

最后读取新运行目录的 `pipeline_report.json` 及两份 `reports/evaluation.json`。恢复数据后 smoke 通过只说明有界数据、训练、评估、保存与加载链路可运行，不能证明训练精度或工程精度达标。smoke 不安装到 `artifacts/`，其随机初始化后仅 4 steps 的模型不能作为可用工程模型。

`Label_PowerConsumption → power`、`Label_Process_Outlet_DP → 处理出口露点` 只进入审计表。它们不进入 X、Y、scaler 或 loss。六个输出以 float32 `[N,6]` 参与训练；X 为 float32 `[N,10]` 或 `[N,9]`。

## 4. 抽样、几何隔离划分与缩放

### 全量划分

- XF 固定外测试组为 `(厚度=300, 直径=1070)`；validation `fold_1` 为 `(200,1070)`、`(400,1070)`、`(400,965)`；其他几何组用于训练。这是固定单次划分，入口不会自动轮转多个 fold。
- 主转轮将实际存在的 `(厚度,直径)` 元组按 Python 元组顺序排序，按几何组数量约 70%/15%/15% 连续分配 train/validation/test；不是随机按行分层。使用 `round(N×0.70)`、`round(N×0.15)` 并保证三个分区非空。同一几何组绝不跨分区；组数比例不保证样本行数比例也为 70/15/15。
- `split_report.json` 保存每分区样本数及几何组；checkpoint 的 `data_context.partition_rows` 还绑定逐条 ID 的分区信息。

### smoke 抽样

`prepare_sample(profile,n=500)` 仍先读取并校验整份权威 XLS，然后只对清洗后的内存副本抽样。它按几何组排序，保留每组源顺序的首/末行，再从剩余样本用固定 `random_state=42` 补足 n；这是源顺序边界覆盖，不能理解为所有特征极值都覆盖。抽样种子固定为 42，独立于训练 CLI 的 `--seed`。过小的 `--sample-size` 可能丢掉必需测试/验证组，应保留默认 500。

### 预处理

仅用训练分区拟合两个 sklearn `MinMaxScaler(feature_range=(-1,1))`。X 直接缩放；Y 先只对 `处理出口含湿量` 做 `log1p`，再对全部六列做 MinMax 缩放。其余五个输出不做 log。逆过程为目标 MinMax 反缩放，再对相同列 `expm1`，返回物理量；不要重复取对数或重复反变换。

scaler 不按验证/测试数据重新拟合，默认不裁剪到训练范围。训练、仿真共用 `dual_rotor_sim/scalers.py` 的列/维度校验及目标变换适配器。新 `scalers.pkl` 只保存原生 sklearn scaler、列名与普通变换状态，不依赖 `training.*` 自定义 pickle 对象。

## 5. 固定模型与默认训练控制

每台转轮各训练一个固定的多输出 KAN，不进行逐输出路由、候选择优或 fallback。KAN 实现在 `training/src/kan_model.py`：每层为 SiLU 残差线性项加 B-spline 项，均匀网格、三阶样条；中间不另加 MLP 隐层激活或归一化。`training/src/` 与仿真 `core/` 中同名 `kan_model.py`、`preprocessing.py`、`feature_engineering.py` 必须逐字节相同，修改时双侧同步核验。

| 项目 | XF | 主转轮 |
| --- | --- | --- |
| 网络宽度 | `10 → 24 → 6` | `9 → 16 → 6` |
| `grid_size` / `spline_order` | 6 / 3 | 5 / 3 |
| `grid_range` | `[-1,1]` | `[-1,1]` |
| 优化器 | AdamW | AdamW |
| learning rate | `5e-4` | `1e-3` |
| weight decay | `1e-4` | `0` |
| 默认最大 epochs | 300 | 200 |
| 早停 patience | 20 次周期验证未改善 | 20 次周期验证未改善 |

共同默认值：`profile=all`、`batch_size=64`、`seed=42`、`device=cpu`、验证间隔 2000 optimizer steps、checkpoint 间隔 2000 optimizer steps。入口不自动选择 GPU；指定 `--device cuda` 前确认本机 PyTorch/CUDA 可用。

损失是变换并缩放后的六输出等权 MSE，没有露点 loss、power loss、能量约束项或逐输出额外权重。梯度范数裁剪为 1.0；损失或梯度非有限立即失败。每个 epoch 对训练行生成可恢复的确定性随机排列，末 batch 可以小于 batch size。学习率固定，当前没有 scheduler。

默认 `fit()` 的总预算为 `max_epochs × ceil(train_rows/batch_size)` optimizer steps，早停按验证事件计数。`--max-steps N` 表示目标总 step；CLI 走 `train_steps()`，训练剩余 `max(0,N-global_step)` 步，该有界路径不启用 patience 早停。它不是 N 个 epoch，也不是恢复后再增加 N steps。

## 6. 评估、最佳模型与日志的含义

周期验证对整个 validation 分区做一次前向，共享预测计算缩放 MSE 和物理尺度六输出指标；不是只验证一个 batch。只有缩放验证 MSE 严格下降才更新最佳模型。`patience=20` 指 20 个验证事件，不是 20 epochs。

结束时有三种评估，`reports/evaluation.json` 与 `run_report.json` 均记录：

| 键 | 实际权重与数据 |
| --- | --- |
| `in_memory` | 训练结束时的内存权重，在 validation 上评估 |
| `checkpoint` | 将最佳 checkpoint 加载到同一个模型对象，在 validation 上评估 |
| `test` | 上一步加载后的最佳权重，在 test 上评估 |

没有周期验证时，最终 checkpoint 充当交付状态；`best_step=0`、`best_validation_loss=null` 表示没有周期验证最佳值，不能解释为最佳误差为零。结束评估不会补写周期验证历史。最终部署文件来自最佳 checkpoint 的 `model_state_dict`，不是盲目保存最后一次 optimizer step 的内存权重。

物理指标为逐输出 MAE、RMSE、NRMSE=`RMSE/(目标最大值−目标最小值)`、R²。预测含湿量三列负值先投影为 0，再计算物理指标/露点；报告保留投影次数和比例，不能用投影掩盖模型问题。目标某输出跨度为零、预测/指标非有限等会报错。Excel 露点独立比较，仅对有限露点预测计算 MAE，并报告可比较数量及预测/目标干燥极限数量；无有限可比样本时露点 MAE 为 `null`。

`reports/power_comparison.json` 将源表 `power` 与“冷吹出口→再生温度”的显热焓差代理做离线偏差、MAE、RMSE、稳健残差异常审计。它用源表再生/冷吹风量，假定 power 为 kW、风量为 m³/h、压力 101325 Pa；代理不是完整系统三股混风加热负荷，也不产生运行时校正系数。异常只标记，不作为额外删除训练数据的理由。

逐步 `train.log.jsonl` 记录 timestamp/profile、step 损失、梯度范数、学习率、step 耗时、验证和 checkpoint 事件；`train_history.json` 保存完整步损失和周期验证历史。指标报告代表本次指定数据分区上的误差，不自动代表未见工况的工程物理验收。

## 7. 执行命令、全量授权与安装行为

有界 smoke：

```bash
.venv/bin/python -m training.single_kan.train \
  --profile all --smoke-test --max-steps 4 \
  --validation-interval-steps 2 --checkpoint-interval-steps 2 --no-progress
```

仅在用户明确授权全量训练后执行：

```bash
.venv/bin/python -m training.single_kan.train --profile all --confirm-full
```

默认全量运行在两个请求 profile 都完成后才开始安装运行时包。旧包移到该次运行 `previous_artifacts/` 留档，无自动回退。安装分包替换不是跨两包的事务；若写入失败，应检查两个运行时包实际状态，不能只看第一包成功就报告整体成功。训练/安装失败在 `pipeline_report.json` 记录，入口退出码 2。

需要全量试跑但保留现有运行时包时，获授权后显式指定一个新的空输出目录：

```bash
.venv/bin/python -m training.single_kan.train \
  --profile all --confirm-full --output-root results/training/人工指定的新运行编号
```

`--output-root` 指向非空目录会拒绝覆盖；无论 smoke/full，都不自动安装。`--profile xf` 或 `--profile main` 只训练/安装该 profile。默认路径下即使增加 `--max-steps` 进行有界全量数据训练，仍属于 full 模式并可能自动安装；想保留当前运行时模型时务必使用显式 `--output-root`。

训练代码不应直接作为长期部署推理入口；仿真默认只读 `artifacts/kan_xf_single/`、`artifacts/kan_main_single/`，加载时核验 profile、输入/六输出、架构及 scaler 列。缺模型会报错，不加载历史候选。

## 8. checkpoint 身份与恢复

可恢复训练文件是 `checkpoints/<profile>/checkpoint.pt`，不是运行时 `model/best_model.pt`。schema v2 checkpoint 包括完整 model/optimizer/preprocessor、训练历史、seed、batch size、验证/保存间隔、batch cursor、当前行排列、Python/NumPy/PyTorch/CUDA 与 batch RNG 状态，以及 `data_fingerprint`、`data_context`。

数据指纹绑定源 SHA、profile、smoke/full、样本范围、清洗后源行顺序、各分区行 ID、实际训练/验证 float32 数组及顺序、模型契约、seed、batch size 和两个 step 间隔。恢复时重新读取真实 XLS 重新构造并核验；缺少身份的旧 checkpoint、替代数据、改变样本顺序/分区/控制参数均拒绝。不能向 trainer 注入占位数组后续训。

`--resume` 支持旧运行根目录、checkpoint 根目录或单 checkpoint 文件。入口先将旧 checkpoint 和同目录 best checkpoint 复制到新运行，再恢复；不会回写旧记录。`--profile all` 恢复两台模型应传旧运行根目录，让入口分别解析两份 checkpoint；不要把某台 checkpoint 文件直接作为两台的共同恢复源。

全量恢复依旧必须明确授权，并带 `--confirm-full`。其余控制参数按照旧运行 `config_snapshot.yaml` 原样提供；只允许把目标总步数增加。例如以下仅适用于旧运行原本也是 main/smoke/500 行、seed=42、batch=64、验证/保存间隔=2、目标 4 steps 的情况：

```bash
.venv/bin/python -m training.single_kan.train \
  --profile main --smoke-test --sample-size 500 \
  --seed 42 --batch-size 64 \
  --validation-interval-steps 2 --checkpoint-interval-steps 2 \
  --resume results/training/已核验的旧运行编号 --max-steps 8 --no-progress
```

若原恢复运行缺少源数据，只能带外恢复相同 XLS 后再恢复。运行时 bare state_dict 不含 optimizer/RNG/数据身份，适合推理，不是精确续训材料。

## 9. 产物结构与文件职责

默认新建的训练运行全部位于 `results/training/`：

```text
results/training/<时间>_<smoke或full>_<profile>_<唯一后缀>/
├── pipeline_report.json
├── checkpoints/
│   ├── xf/{checkpoint.pt,best_model.pt}
│   └── main/{checkpoint.pt,best_model.pt}
├── kan_xf_single/
│   ├── model/
│   │   ├── best_model.pt
│   │   ├── scalers.pkl
│   │   ├── scaler_meta.json
│   │   └── metadata.json
│   ├── model_metadata.json
│   ├── config_snapshot.yaml
│   ├── train.log.jsonl
│   ├── run_report.json
│   └── reports/
│       ├── cleaning_report.json
│       ├── split_report.json
│       ├── train_history.json
│       ├── evaluation.json
│       └── power_comparison.json
├── kan_main_single/             # 与上同结构
└── previous_artifacts/          # 默认 full 安装时，保存实际存在的旧运行时包
```

`checkpoints/*/best_model.pt` 只在周期验证改善后创建；没到验证间隔的短运行可能没有它。两台 profile 按顺序训练，单 profile 的运行不会生成另一台目录。`pipeline_report.json` 的 `running/completed/failed`、`failures`、`runtime_artifacts_updated` 是汇总依据；意外终止留下 `running` 不能当作成功。

安装后的运行时结构为：

```text
artifacts/
├── kan_xf_single/
│   ├── model/{best_model.pt,scalers.pkl,scaler_meta.json,metadata.json}
│   ├── model_metadata.json
│   ├── config_snapshot.yaml
│   └── training_run.json
└── kan_main_single/             # 同上
```

运行时 `model/best_model.pt` 是 bare state_dict，可 weights-only 读取；训练 checkpoint 是包含状态字典的完整 payload。`model_metadata.json` 记录 schema/profile、原始输入列、六个 `direct_outputs`、派生露点、审计列、源技术键、架构和源 SHA；`model/metadata.json` 同步保存模型元数据。`scaler_meta.json` 记录列序、feature range、log1p 列。`config_snapshot.yaml` 保存本次配置，`training_run.json` 指回训练记录，仅作追溯，不是仿真加载门禁。

当前不使用 `routing.json`、registry、逐输出候选或 promotion 清单。运行时包不混入日志和续训 checkpoint。以上所有训练/运行时二进制和运行报告均为本地生成物，不推送到本次纯源码 GitHub 仓库。后续 ONNX 导出应从核验过的完整运行时模型包读取权重和 scaler，接口转换与 DLL 规范见同目录部署移交文档。

## 10. 接手时的验收边界与常见问题

| 现象 | 正确处理 |
| --- | --- |
| clone 后 pytest 部分用例显示 skip | 核对 `requires_data`/`requires_models` 外部资料缺口；skip 不属于该集成验证成功 |
| 严格模式找不到 XLS/历史模型 | 按用例固定路径带外恢复；不要生成占位数据或换模型冒充所需资料 |
| clone 后仿真缺模型 | 带外恢复已核验包，或获全量训练授权后训练生成；不指向历史 archive |
| SHA 不一致/有效行数错误 | 检查传输、文件名、原始字节及工作表，不修改契约常量迎合文件 |
| smoke 通过、精度很差 | 4 steps 只验证管线；不能安装后宣称工程模型可用 |
| `best_validation_loss=null` | 无周期验证最佳值；检查间隔与步数，保留真实状态 |
| 续训指纹不一致 | 核对原 XLS、样本/分区/数组顺序及控制参数；需要改身份时新开训练 |
| full 结束但安装失败 | 保留本次完整运行与旧包，分别检查两台 artifacts 实际状态 |
| 非负投影很多/干燥极限很多 | 查看原始模型质量与分区误差，不能只看露点有限样本 MAE |

训练精度、整机数值收敛、Python→ONNX/.NET 数值迁移、封装功能验证、工程物理验收是不同结论，必须分别列证据。本文说明当前可执行流程，没有宣称任何当前模型已经达到工程精度。
