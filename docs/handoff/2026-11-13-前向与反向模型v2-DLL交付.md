# 前向与反向模型v2 DLL交付

2026-11-13按用户要求完成Windows x64/.NET 8托管DLL封装，两个程序集和交付包分别命名为**露点与能耗预测模型v2**和**最优能耗工况搜索模型v2**。业务包版本统一为2.0.0；不依赖Python运行时，宿主须为.NET 8，不能直接作为native C ABI或.NET Framework 4.x DLL引用。

本轮用户随后明确授权“任务完成后上传到github”。本次源码、接口、构建/打包脚本和验证说明允许同步至既有仓库；模型、ONNX、DLL、NuGet、ZIP、原始数据和生成结果继续按交接约定本机交付。此前“仅本机”要求作为历史保留，本次上传授权以用户最新指令为准。

## 源码和API

| 工程 | 程序集 | 公开入口 |
|---|---|---|
| Dehumidifier.Prediction | 露点与能耗预测模型v2.dll | Dehumidifier.Prediction.PredictionModel |
| Dehumidifier.Optimization | 最优能耗工况搜索模型v2.dll | Dehumidifier.Optimization.EnergyOptimizer |
| Dehumidifier.Simulation | Dehumidifier.Simulation.dll | 共享ONNX与整机物理核心 |

前向支持完整schema v2 JSON字符串/文件配置，同步、异步和取消，返回最终Supply、露点、六项热负荷、收敛信息及JSON/PNG路径。输入温度℃、含湿量g/kg干空气、风量m³/h、尺寸mm，负荷kW。`SimulationConfig.Parse`公开并继续严格拒绝未知字段。三个湿度保留图内Softplus结果，逆变换后若出现负值报`MODEL_OUTPUT_INVALID`，不再沿用旧C#事后Math.Max截零。

前向与反向共用主转轮→CC3后表冷→Heater_Post后加热→Supply拓扑。末端按目标温度自动冷/热，六项负荷全部计入。旧前向配置未给目标时兼容旁通，优化必须同时给目标露点和温度。

反向为纯C#有界差分进化和坐标细化，支持控制边界、0.1℃网格、随机种子、预算及可选初值。默认仍搜索CC1、CC2、新风再生、主轮再生四个温度，固定入口、风量、尺寸、转速。目标为`J=Q_sum/Q_ref+0.1*w(e)*abs(e)/(1℃)`，分区权重/边界和±1℃硬约束沿用[当前物理与优化契约](2026-11-11-末端调温与分区加权优化.md)。Q_ref整次只建立一次；最终Supply、收敛和未裁剪RH门禁保持。候选不逐次写图，最佳候选绕过缓存完整复算并留档，不能把无解或独立复算失败当作成功。

C#使用System.Random的best/1/bin差分进化，Latin hypercube初始化、F∈[0.5,1)、CR=0.7；与SciPy/NumPy随机轨迹不同，因此不承诺同种子相同路径或相同最优点，也不证明全局最优。最佳点可作为下一次初值，但仍重新计算，未硬编码模型结果。

完整调用示例见[DLL调用说明](../../deployment/dotnet/docs/v2模型DLL调用说明.md)。`samples/V2DllConsumer`仅以Reference/HintPath引用实际二进制，没有ProjectReference，已实际发布和运行验证。

## 重建和封装

遵循[ONNX与DLL交付流程](ONNX与DLL交付.md)：正式模型身份核验→本次导出与参考→Windows restore/build/test/publish/pack→真实运行与故障检查→原阈值严格迁移→成品组装/ZIP逐文件回读。

本次本机原无SDK，使用微软官方dotnet-install脚本将.NET SDK8.0.428安装到`results/deployment/20261113_v2_dll/toolchain/dotnet`，未使用旧业务DLL。六个ONNX/契约文件暂存到被忽略的`src/Dehumidifier.Simulation/models`。每台257样本导出验证通过，最大物理差XF7.28e-5、main6.66e-5，低于原1e-3门槛，模型权重/scaler不变。

```powershell
# 先按既有流程导出到新的运行目录并暂存models，再执行：
.\deployment\dotnet\build_v2.ps1 -Output .\results\deployment\新的运行编号\windows
python deployment/dotnet/package_v2_delivery.py --build results/deployment/新的运行编号/windows --models results/deployment/新的运行编号/onnx --validation-report results/deployment/新的运行编号/reports/strict_migration_all_cases.json --runtime-report results/deployment/新的运行编号/runtime_validation.json --examples results/deployment/新的运行编号/configs --output results/deployment/新的运行编号/交付
```

`build_v2.ps1`先执行原build.ps1的核心测试、验证器、WinForms发布及NuGet步骤，再测试/打包两个入口、发布自包含V2Verify。没有SkipTests入口。`package_v2_delivery.py`要求全新父目录，校验verify/v2verify/WinForms的模型六文件和核心DLL一致，分别生成两个中文目录、ZIP、manifest及zip.sha256，CRC和每个文件SHA回读均检查。运行报告须显式给`windows_runtime_validation_passed`布尔值，严格迁移状态单独保存，不能由打包成功推断通过。

每包含`dll/`对应入口和必要依赖、`models/`六文件、完整自包含`verify/`、对应NuGet+core包、示例、维护源码及验证报告。通用verify会引用两个入口，因此其目录保留两入口DLL。前向包另含WinForms示例；反向包以搜索API和控制台为入口。NuGet未收齐全部离线传递依赖，不宣称空缓存离线restore已通过。
