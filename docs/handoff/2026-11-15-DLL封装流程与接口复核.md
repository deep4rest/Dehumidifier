# DLL封装流程与接口复核（2.0.2）

本次按用户要求重新检查Python到DLL的完整链路、接口与模块调用，并在交付包内提供简明使用说明和可运行示例。

结论：发现并修正了在线缩放路径、模型配套校验、单包联调依赖和对象接口校验问题。实际DLL可以运行，QY1070搜索与同配置前向一致；**PyTorch与ONNX整机严格迁移尚未全部通过，本次5组为0/5**，不能认定Python业务系统已被逐字段无差异迁移。旧版本的通过比例只对当次工况和二进制有效。

## 封装实际如何工作

两个业务入口并不是把全部Python代码转换成DLL：Python中的两台转轮KAN及湿度非负头导出为`xf.onnx`/`main.onnx`，C#负责物理输入缩放、图推理、逆变换及整机元件/联立求解。预测入口调用共享`Simulator`；搜索入口在同一个`Simulator`上搜索四个具名控制温度，启用CC3/Heater_Post末端。C#优化器与SciPy采用相同目标和约束，随机轨迹不同，不承诺同种子同最优点。

两业务DLL继续为.NET8托管入口，Windows x64，无Python运行时依赖；不能直接按原生P/Invoke或.NET Framework 4.x DLL调用。源权重、scaler、原始工况、拓扑、物性、求解容差及露点±1℃约束未改，没有重训。

## 确认并修正的问题

| 问题 | 修正 |
| --- | --- |
| 导出验证走训练侧float64物理输入，正式运行先转float32；C#又提前将系数转float32 | 导出复用正式`SingleRotorModel`的scaler；C#按正式在线路径先转输入float32，乘float64系数后舍入float32，再加float64偏移并舍入float32 |
| 运行时只校验契约列维度，没有绑定真实图/预处理文件，也未检查预处理自身列序、clip等 | 新部署schema2绑定ONNX、汇总/分项预处理SHA；验证列序、分文件一致性、clip=false、唯一log1p列、正缩放系数、输入/输出张量类型形状；不配套即拒绝加载 |
| 单个产品的dll目录只含本入口，文档的搜索→预测联调却需要另一入口；旧验证从完整verify目录引用DLL，掩盖此缺口 | 每包dll目录提供配套双入口+共享核心+依赖，附只引用该目录的`接入示例`；三个业务NuGet同时提供 |
| NuGet仅检查文件存在，运行报告可与实际构建不对应 | 封装逐字节核对NuGet内DLL和core包内六模型文件；成功报告必须绑定本次三个程序集及六文件SHA，错配或无身份不接受通过结论 |
| C#对象入口的四个控制温度没有像JSON入口那样提前拒绝NaN/Infinity | `SimulationConfig.Validate`统一在模型调用前报CONFIG_INVALID |

原标准化输入的最大差2.980232238769531e-7；257×9个值中旧C#与正式Python不同的数量为XF1231、main1116，旧导出验证边界则为XF1615、main1096。这个证据说明路径不一致，不足以认定开发端此前−40℃的确切原因。

图本身重新导出后SHA与既有正式图一致；变的是导出验证边界、预处理描述/绑定契约和C#缩放过程。2.0.2必须整套更新`dll`与`models`，旧schema1仅适用于旧版本。

## 实际验证

- Windows SDK8.0.428真实restore/build/test/publish/pack，C#核心34、前向6、反向25，共65通过；部署Python测试15通过。
- 两转轮各257个原始物理样本经实际DLL推理。对正式PyTorch单条预测，六输出最大物理差XF9.34853e-5、main7.17640e-5，均低于原1e-3；对相同batch=1的Python ONNX最大差约1.6653e-16。最初用ONNX batch257对C# batch1要求逐位一致失败，改为相同调用形状后原严格1e-9门槛通过，未放宽阈值。
- QY1070两组目标−45/−35和−50/−40℃均实际搜索，再另启预测DLL进程读取完整BestConfig；所有物理记录一致。当前第一组预算内候选CC1/CC2/Oa/Low=9.4/15.9/90.2/100.5℃，露点−45.04990574022008℃、温度−35℃，Q_sum270.14408025438365kW、Q_ref294.749151555896kW、J0.9170210518791001。不是全局最优证明，也不能与旧1220mm参数混用。
- 重新比较五组PyTorch/C#整机记录：QY原工况18/17次、default17/18次；当前QY最佳及其25℃加热/−55℃冷凝分支16/15次。后三组同一上游的history含湿量残差最大差1.1563806165e-5g/kg，超过原1e-5阈值。故严格0/5，未删除history、改迭代断言或放宽容差。单轮误差通过及DLL内前反向一致，不代表该严格迁移通过。

当前训练域覆盖、水/焓失衡、理想末端设备容量/结霜/COP限制继续保留；未做整机实测验收、空白Windows机验收或空缓存NuGet离线restore。ONNX原生库依赖VC++v14 x64运行库，成品自包含的是.NET运行时，不代表没有其他系统依赖。

## 交付给开发怎么使用

每包根目录首先阅读`快速使用.md`，只列运行、C#接入、单位、结果判断和常见错误。双击`01_前向预测.cmd`计算原始QY1070；双击`02_搜索并前向复算.cmd`执行−45/−35目标并自动复算，对照两次露点。`run_example.ps1`采用UTF-8 BOM兼容Windows PowerShell5.1；cmd正文采用ASCII路径，避免中文代码页干扰。`接入示例/V2DllConsumer.csproj`默认引用旁边dll目录，不需要仓库源码或NuGet业务包，开发机需要.NET8 SDK。

宿主使用EXE同目录的全部依赖DLL和`models`文件夹；入口程序集与模型要配套，不能借用其他目录的同名文件。两边始终采用完整QY1070配置，搜索后直接传`BestConfig`或读取`BestConfigPath`；HeaterOa是新风再生，HeaterLow是主轮再生，按名称映射，不按不同构造函数的位置顺序搬运。

完整API继续见[DLL调用说明](../../deployment/dotnet/docs/v2模型DLL调用说明.md)。原始九列ONNX输入和scaler由DLL处理，业务宿主输入物理单位schema v2 JSON，不自行二次归一化。

本机证据根`results/deployment/20261115_dll_audit`：`preprocessing_before.json`、`onnx`/`export.log`、`windows_final`/`build_final.log`、`rotor_dll_validation_final.json`、`runtime_validation_final.json`、`reports/strict_migration_final.*`、`python_tests_final.xml`。候选成品独立解压后验证双击脚本及其dll目录引用工程；正式交付在`交付`，包含两份中文目录/ZIP与manifest/SHA。源码/说明按既有授权同步GitHub，模型/数据/二进制及生成结果仍仅本机。
